# 小说创作工作台使用手册

适用版本：1.0.1。维护者：lost-dream。更新日期：2026-10-21。

[项目首页](../README.md) · [版本下载](https://github.com/lost-dream/story-workbenches/releases) · [来源与许可](../NOTICE.md)

## 先选一个起点

| 你现在的情况 | 使用哪个技能 | 第一条请求 |
|---|---|---|
| 想写长篇，还没有稳定方向 | 长篇工作台 | 先讨论题材和核心冲突，只做方案 |
| 已有想法，想定大纲 | 长篇工作台 | 给出已定设定、目标篇幅和本轮规划范围 |
| 长篇已经写了一部分 | 长篇工作台 | 导入旧稿，保留已写正文，重建续写工程 |
| 想写一篇完整短篇 | 短篇工作台 | 说明目标情绪、题材、人称和字数，先构思或直接授权成稿 |
| 短篇写到一半 | 短篇工作台 | 导入残稿，确认未完成范围，再准备续写 |
| 只想审稿、润色或设计封面 | 对应篇幅工作台 | 直接说具体任务，不必从头跑流程 |

## 1. 这两个 skill 是什么

它们把小说创作的方法、模板、参考资料与检查脚本整理为两套 Codex 技能。你通过对话指定任务，Codex 读取相应流程并在你的项目文件夹中工作。

`story-long-workbench` 处理扫榜、拆文、长篇规划、章节写作、日更、导入、去 AI 味、审稿和封面。`story-short-workbench` 处理短篇构思、小节大纲、成稿、精修、导入、分析适配、去 AI 味、审稿和封面。

工作台以对话和文件协作为主，没有独立图形界面。故事的关键设定、人物命运和结局仍由作者决定。运行效果取决于使用的模型、工具、输入材料和项目状态。

## 2. 安装与检查

### 推荐：让安装器处理目录

在 Codex 中发送：

```text
使用 $skill-installer，安装这个仓库中的两个 skill：
https://github.com/lost-dream/story-workbenches

技能路径：
skills/story-long-workbench
skills/story-short-workbench
```

也可以只指定其中一个。安装器报告已存在同名技能时，先保留你的自定义修改，再决定更新，不要强制覆盖。

### 手动安装

从 Releases 下载完整包或单独技能包，解压后把两个同名技能目录完整放进宿主实际扫描的 skills 目录。当前官方文档列出的用户级位置是 `~/.agents/skills/`，项目级位置是项目中的 `.agents/skills/`。不同版本或安装器可能使用已有目录；已经能识别时不要为了路径一致再重复安装。[官方本地技能说明](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)

目录应类似：

```text
skills/
├── story-long-workbench/
│   ├── SKILL.md
│   ├── LICENSE
│   ├── NOTICE.md
│   ├── agents/
│   ├── modules/
│   └── references/
└── story-short-workbench/
    ├── SKILL.md
    ├── LICENSE
    ├── NOTICE.md
    ├── agents/
    ├── modules/
    └── references/
```

不要只复制 `SKILL.md`，也不要让入口多套一层同名目录。Codex 可按请求匹配技能，也可以用 `$技能名` 明确指定；新安装未出现时可重启宿主再检查。[官方技能调用与安装说明](https://learn.chatgpt.com/docs/build-skills)

### 验证入口

```text
使用 $story-long-workbench，列出支持的创作阶段，暂时不要创建小说文件。
```

```text
使用 $story-short-workbench，说明导入短篇残稿后，开始续写前需要哪些材料。
```

能读取流程并说明范围，代表入口已可用；这不等于所有采集脚本、图片工具都已配置完成。

## 3. 准备小说项目

给每部作品一个独立文件夹，并让 Codex 在该文件夹所属的工作区执行任务。小说产物不要存进技能安装目录。

第一次说明四件事就够：作品当前状态、想完成的事、本轮范围、必须遵守的限制。路径用你的实际路径替换，示例中的书名与情节都只是演示。

通用请求模板：

```text
使用 $story-long-workbench。
项目目录：<我的小说目录>
当前状态：<刚有想法 / 已有大纲 / 已写到第几章>
本轮任务：<讨论结构 / 细纲 / 正文 / 导入 / 审稿>
范围与停点：<具体章节或产物，完成后停在哪里>
已定内容：<题材、平台、人物、字数、人称>
约束：<不能改的事实、不能提前揭示的真相、不要新增的设定>
```

换成短篇任务时使用 `$story-short-workbench`，把范围写成全篇或具体小节。

## 4. 长篇从零开书

### 4.1 先讨论方向

```text
使用 $story-long-workbench。
我想写一部长篇都市悬疑，主角是夜班档案员。
请给出2个核心冲突方向，分别说明主角目标、持续阻碍和长线悬念。
先只讨论，不建工程，不写正文。
```

题材不确定且希望参考市场时，可以先扫榜；已有清楚方向时可以直接规划。

### 4.2 按需扫榜

```text
使用 $story-long-workbench，研究起点近期新书中的悬疑方向。
请使用当前能获取的真实榜单样本，记录来源和采样日期，比较反复出现的卖点。
给出2到3个候选选题，并说明样本不足处、写作难点和验证方法。
这轮只扫榜和选题，不拆书、不写正文。
```

需要相应网络与浏览器能力。部分榜单取不到时，报告应说明覆盖范围；旧参考资料和单本排名不能直接当成当前趋势。不要跨平台混用口径，也不要将长篇榜单当作短篇市场结论。

### 4.3 设定、卷纲与细纲分层完成

```text
使用 $story-long-workbench，采用刚才确认的第一个方向。
计划约40万字，第三人称，核心真相保持到中后期再揭示。
这轮只整理核心设定和全书大纲，列出仍需我决定的问题，不展开章节正文。
```

```text
使用 $story-long-workbench，为第一卷规划剧情单元和卷纲。
沿用现有设定，不改变结局方向。这轮不出细纲、不写正文。
```

```text
使用 $story-long-workbench，依据已确认卷纲，生成第1到3章细纲。
每章写清目标、阻碍、行动、代价和结尾期待。只做这三章，完成后停止。
```

“帮我开书”默认走规划确认流程，最远到首批细纲；明确要求正文后才进入章节写作。想一次完成多个规划层级，可以直接写明本轮授权范围。

### 4.4 写指定章与日更

```text
使用 $story-long-workbench，按已确认的第1章细纲写正文。
字数2200到2600字；不得揭示凶手，不新增主线人物。
缺少必要设定或追踪状态时先补齐有依据的前置，再完成本章和检查。
只写第1章。
```

```text
使用 $story-long-workbench，继续当前长篇，本轮写第4到5章。
先核对已有正文、对应细纲和追踪状态，按章串行完成，不提前写第6章。
```

日更需要已有正文和可用追踪。未指定数量时按模块的小批次规则执行，单轮最多3章；要写更长范围时分轮续接。不要手动改追踪脚本生成的派生视图，发现错误时让工作台从证据修订权威状态。

## 5. 分析参考小说

```text
使用 $story-long-workbench，分析 <参考小说文件路径> 的前三章。
重点看开篇问题、人物目标、信息释放和结尾期待。
引用具体原文位置，区分事实与推断，不延伸到全书分析。
```

```text
使用 $story-long-workbench，对 <原文路径> 做完整拆解。
按连续章节块完成，保留可续跑进度；已授权的分析阶段一次接着做。
原文缺失或证据不明时如实记录，不编造后续内容。
```

已有拆文成果会先检查能否复用，按需补缺。分析产物通常在 `拆文库/{书名}/`；它可以支持后续规划，不是自动改写参考作品的指令。建立灵感库属于可选后置任务，需要时再提出。

## 6. 导入自己的长篇旧稿

```text
使用 $story-long-workbench，导入我已经写好的长篇《夜班档案》。
原文位置：<文件或文件夹路径>。
第1到20章完整，第21章是残稿；先保留残稿，不把它算作完整章。
目标是整理成可续写工程。保留原文，反推的设定单列待确认。
这轮完成导入和核对，不继续写第21章。
```

导入会识别来源与范围、分析已写内容、迁移项目结构并初始化长篇追踪。卷界、残稿处理或人物关系存在实质歧义时需要作者决定。超过200章的作品可能约定首期深拆范围与其余章节的简化摘要，汇报应区分两者。

通常可以看到这些产物，具体文件以实际任务为准：

```text
作品目录/
├── 设定/
├── 大纲/
├── 正文/
├── 追踪/
└── .story/work/
```

导入自己的书属于重建续写基线，不会自动将它登记为外部对标书。导入记录尚未完成时说“继续导入”，不要重新创建同一本书的第二套工程。

## 7. 从构思到短篇成稿

### 7.1 先锁定读者感受

```text
使用 $story-short-workbench，设计一篇8000到10000字的悬疑短篇。
第一人称，目标情绪是反转后的震撼，场景集中在一栋旧公寓。
先给故事核、人物动机、主要线索和小节大纲，不写正文。
```

目标情绪可以直接说成“读完有点遗憾”“想看报应兑现”或“希望最后温暖一些”。已经说明过的内容不必重复选择。字数、人称和结局红线以你的明确要求为准。

### 7.2 设计确认后写正文

```text
使用 $story-short-workbench，按当前已确认的设定和小节大纲写完整正文。
总字数8000到10000字，保持第一人称，不新增核心反转。
如果设计字段还缺少有依据的内容，先补齐必要前置并检查，再进入正文。
涉及改变结局或人物动机的选择先问我。
```

短篇通常围绕 `设定.md`、`小节大纲.md`、`正文.md` 三个核心文件工作，不建立长篇式的卷纲目录或逐章追踪。正文可能分小节、分批完成，这不意味着可以把一篇未写完的内容称作完整交付。

### 7.3 导入短篇残稿

```text
使用 $story-short-workbench，导入 <短篇原稿路径>。
全文尚未写完，目前到第6节。保留已写内容，整理三文件工程。
请区分“已经导入”和“已经可以续写”，列出未定结局、后续节次或其他设计缺口。
这轮不续写。
```

开始续写前，原文能够确定的设计可以直接补齐；未写结局、反转位置、目标篇幅或付费断点等新决定不能冒充原稿事实。设计验收通过、未来范围确定后再进入正文。完整稿可以先导入再审查，不需要为了继续流程凭空续上一节。

## 8. 审稿与去 AI 味

这两类任务可以直接进入。

仅审稿：

```text
使用 $story-long-workbench，单人审查第1到3章。
重点检查人物动机、时间线、规则漏洞和信息提前泄露。
每条问题给出原文位置、引文和修改方向，只出报告，不修改正文。
```

仅检测表达：

```text
使用 $story-short-workbench，检查 <正文路径> 的模板化句式和AI味。
只做检测和分级，给出有原文依据的问题，不改文件。
```

实际去味：

```text
使用 $story-short-workbench，润色 <正文路径>。
保留剧情、人物、信息差、伏笔和结尾，不新增事件。
只调整确实影响读感的表达，保留有叙事功能的判断句和钩子。
完成后说明主要改动，不能确定的地方列给我看。
```

去 AI 味以表达修改为目标，不承诺任何第三方检测分数。审查默认由当前会话执行；明确要求多个助手时，还需要宿主实际提供相应能力。少量章节可同批检查，超出阅读容量再分批，并用落盘状态衔接。

## 9. 设计小说封面

只要方案或提示词：

```text
使用 $story-long-workbench，为《夜班档案》设计封面提示词。
作者名：<我的笔名>；题材：都市悬疑。
希望以旧档案袋和深夜办公室为主要元素，书名醒目。
先给2个构图方向，不调用图片工具。
```

实际生成时，在同一请求中补充：

```text
本次使用内置 image_gen 生成第一种方案。
目标平台：<平台>；若要做上传版，先核对当前规格。
文件放在我的小说目录内，保留原图。
```

也可以明确选择 Image2 API。没有选择时会先询问，整个任务或批次沿用你的选择。技能不附带图像服务，必须由当前宿主提供可用工具。书名、笔名缺失时不会编造，生成后还需要核对文字与裁切安全区。

## 10. 换对话后继续工作

```text
使用 $story-long-workbench，继续 <项目目录> 的当前作品。
先读取实际项目状态、已有正文、大纲和追踪。
告诉我目前到哪里，再准备第12章的细纲，这轮不写正文。
```

短篇则优先读三份核心文件与已写小节摘要；导入任务优先读导入记录。新对话不必复述整本小说，但要给出正确项目目录与本轮任务。上下文文件丢失时不能只靠“上次写到哪里”的口头记忆拼接事实。

## 11. 常见问题

| 情况 | 处理方法 |
|---|---|
| 找不到技能 | 检查扫描目录、目录层级与根部 SKILL.md；用明确技能名；必要时重启宿主 |
| 同名技能显示两份 | 检查是否安装到多个扫描目录，保留需要的一份及自定义改动 |
| 开书后停在大纲 | 默认规划不会自动授权正文；明确请求写哪一章 |
| 续写前要求补细纲或状态 | 这是缺失的必要前置；先据已有材料补齐，不让模型绕过检查 |
| 短篇导入完成却不能马上续写 | 查看导入交接中的设计缺口，先确定未来范围并补齐验收 |
| 提示 Python 或 Node 不可用 | 配置相应运行时后重试；不要把没跑成的检查当作通过 |
| 榜单取不到 | 使用可用网页工具或你提供的样本，报告限制；不能用历史知识冒充实时数据 |
| 想扫短篇市场 | 本包没有新增短篇榜单采集器，可按需求研究真实短篇样本 |
| 无法生图 | 先交付方案与提示词，检查当前选择的图片工具，不自动切换服务 |
| 修改后的句子仍不自然 | 点名段落、说明读感问题和要保留的功能，再做定点修改 |

## 12. 更新、来源与使用范围

更新前备份自己对技能的修改；下载新版本，替换对应技能目录，避免将不同版本的模块混用。小说项目应独立保存，不跟技能包一起覆盖。

本项目基于 [zenstory-ai/oh-story-claudecode](https://github.com/zenstory-ai/oh-story-claudecode) 的部分技能整合，保留上游 MIT 许可与原版权声明，整合与新增文档由 lost-dream 维护。详细对应关系见 [来源说明](../NOTICE.md)，源文件校验值在各技能的 `references/sources.json` 中。使用第三方小说或图片时，另行确认这些素材自身的使用条件。

当前已有的验证包括结构、资源链接、脚本语法、部分脚本样例及六类使用场景的独立流程复核。完整小说、实时平台抓取与实际生图效果需要在你的环境中验证。
